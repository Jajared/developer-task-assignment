# backend

Express 5 on Bun, Prisma 7 over Postgres, Zod validation, Winston logging,
`http-errors` for status codes, `@google/genai` for skill inference.

## Layout

```
db/schema.prisma          # source of truth for tables AND types; migrations/ beside it
db/seed.ts                # idempotent: upserts skills, fills empty tables
prisma.config.ts          # schema/migrations paths + DATABASE_URL — required by Prisma 7
src/
  app.ts                  # createApp(): middleware, /health, routers, JSON 404, error handler
  index.ts                # listen + graceful shutdown
  db/prisma.ts            # PrismaClient singleton (PrismaPg adapter, cached on globalThis)
  generated/prisma/       # GITIGNORED, regenerated by postinstall — never edit
  lib/env.ts              # the only place process.env is read; Zod-parsed, throws at boot
  lib/constants.ts        # MAX_SUBTASK_DEPTH, MAX_SUBTASKS_PER_TASK, MAX_TASKS_PER_CREATE
  lib/validate.ts         # parseOrThrow(): ZodError → 422 with flattened field errors
  lib/log.ts              # logger, getLogger(), describeError()
  lib/request-logger.ts   # request id, req.log, access line
  lib/llm.ts              # generateStructured(): Gemini + Zod; knows no domain
  services/<name>/        # <name>.route.ts, .controller.ts, .service.ts, .validator.ts
```

Services: `tasks/` (create, read, assign, set status — no delete, no edit),
`developers/` and `skills/` (read-only; seeded reference data). `skills/` also
owns `inferRequiredSkillIds()`.

## Prisma 7 gotchas

- Schema is at `db/schema.prisma`; `prisma.config.ts` makes that work. Don't
  move or delete it.
- `DATABASE_URL` comes from `prisma.config.ts` reading `process.env`, not the
  schema. Run the CLI through package scripts so Bun loads `.env`.
- Generated model types are suffixed: `TaskModel`, from `generated/prisma/models.ts`.
  Enums are const objects with lowercase keys from `generated/prisma/enums.ts`
  (`TaskStatus.in_progress`).
- Relations are loaded with inline `include` on each query; there is no shared
  select constant.
- Keep `prisma` pinned to `^7` — a bare `bun add -d prisma` picks an `8.x` prerelease.

## Conventions

- **Layers stay in their lane.** Controllers do HTTP; services own every Prisma
  call; validators own request shape. Routes are just `path → controller`.
- **Services export plain named functions** (`listTasks`, `findTaskById`,
  `createTask`…) with inferred return types. No DTOs, no `.types.ts`, no
  mapping step: Prisma rows go straight to `res.json()`, so a new schema column
  is public immediately.
- **Services throw, never return failures.** Use `http-errors` named
  constructors (`NotFound`, `UnprocessableEntity`, `Conflict`); attach context
  with `Object.assign(new Conflict(msg), { details })`. The handler in `app.ts`
  sends `{ error, details }` for any exposed `HttpError`; everything else is a 500.
- **Validators are functions, not middleware:** `validateCreateTask(payload)`
  built on `parseOrThrow`. Types are `z.infer` with a `T` prefix (`TCreateTask`).
  Derive enums from Prisma (`z.nativeEnum`), `.trim()` strings, human-readable
  messages. Every `:id` route calls `validateTaskId(req.params)` first, so a
  bad uuid is a 422, never a Postgres error.
- **Controllers** take `(req, res, next)`, wrap the body in `try`/`next(error)`,
  and are exported in one block at the bottom of the file.
- **Imports carry `.ts`.** Cross-folder imports use `@/` (maps to `src/`);
  siblings stay relative.
- **Log through Winston, never `console`.** `req.log` in handlers,
  `getLogger()` in services/libs (same request-scoped child via
  AsyncLocalStorage), `logger` at boot. Context goes in a meta object; wrap
  thrown values with `describeError()`. Levels: `error` bugs, `warn`
  degraded-but-handled, `info` handler entry and business events, `http`
  access lines, `debug` anything echoing user input. Every business event is
  logged once, in the service that performs it.

## Status codes

201 create · 404 missing row · 422 Zod failure or body naming a row that
doesn't exist · 409 a rule refused a valid request. Two rules, both in
`tasks.service.ts`, neither enforced by the database:

- **Assignment** (`assertAssignable`): assignee must hold every required skill,
  judged against the state *after* the write. Response
  `details.missingSkills: [{ id, name }]`.
- **Completion** (`assertCompletable`): a task may be `done` only when every
  direct subtask is. Response `details.unfinishedSubtasks: [{ id?, title, status }]`.
  Reopening a `done` task reopens every `done` ancestor to `in_progress` in the
  same transaction; the client gets back only the row it changed.

Any new write path must run the same checks.

## Skill inference

A create body node (root or subtask) with no `requiredSkillIds` gets them
inferred from its title by Gemini. `createTask` runs in order:
`assertTreeWellFormed` (depth, completion rule, referenced rows exist — no LLM)
→ `fillInferredSkills` (parallel per skill-less node) → `assertTreeAssignable`
over the filled tree. Consequences:

- Inference **never fails a create**: no key, timeout (10s), quota, off-shape
  reply all log a warning and leave `[]`. Explicit skills never trigger a call.
- The assignment rule sees inferred skills, so assignee + no skills can 409.

`lib/llm.ts` is the only module that knows Gemini exists; `skills.service.ts`
owns the rule and constrains the model to `z.enum` of existing skill names.

## Routes

```
GET    /health
GET    /api/tasks                  flat list, newest first; every row carries parentId
GET    /api/tasks/:id
POST   /api/tasks                  201; body may nest `subtasks`, whole tree in one transaction
PATCH  /api/tasks/:id              { assigneeId } only (null unassigns)
PATCH  /api/tasks/:id/status       { status } only — registered BEFORE /:id
GET    /api/developers[/:id]       with skills
GET    /api/skills[/:id]
```

Subtasks are created only inline with their root; there is no route to attach
one later or set `parentId`. Title, description and required skills are fixed
at creation. Reads nest `assignee` and `requiredSkills` as whole rows.

## Database workflow

Edit `db/schema.prisma` → `bun run db:migrate` (from this folder; also
regenerates the client) → update `frontend/types/` by hand.

## Testing

`bun test` from this folder (script sets `NODE_ENV=test` and blanks
`GEMINI_API_KEY`). Four suites, next to the code they cover:

- `lib/llm.test.ts`, `services/tasks/tasks.validator.test.ts` — pure.
- `services/tasks/tasks.test.ts`, `services/skills/skills.test.ts` — HTTP over
  `createApp().listen(0)`; **need a running, seeded database**.

Rules for HTTP tests: stub the model with `spyOn(llm, "generateStructured")`
and `spyOn(llm, "isLlmConfigured")` — no test may depend on a key; pick
fixtures by shape from the API (a one-skill developer, a skill they lack),
never by seeded name or id; suffix titles with `unique()`; create trees via
`createTree()` so `afterAll` cascades them away; never assert absolute row counts.
